# Contributing to SinterDB

Thank you for your interest in contributing to SinterDB.

SinterDB is still in active early development, so contributions may involve changing APIs, internal behavior, documentation, tooling, or project structure as the ecosystem evolves.

## Ways to Contribute

You can contribute by:

- Reporting bugs
- Suggesting features
- Improving documentation
- Fixing issues
- Improving tests
- Improving developer tooling
- Reviewing pull requests
- Contributing to SinterDB-related projects across the organization

## Before You Start

Before working on a larger change, consider opening an issue or discussion first.

This helps avoid duplicated work and makes it easier to confirm whether a proposed change fits the direction of the project.

Small fixes, documentation improvements, and straightforward bug fixes usually do not require prior discussion.

## Issues

When reporting a bug, include as much useful information as possible, such as:

- The affected project
- The version or commit you are using
- Your environment
- Steps to reproduce the problem
- Expected behavior
- Actual behavior
- Relevant logs or error messages

Please search existing issues before creating a new one.

## Pull Requests

Pull requests should:

- Focus on a clear change
- Avoid unrelated modifications
- Follow the existing style and structure of the project
- Include tests when appropriate
- Update documentation when behavior or public APIs change
- Pass the repository's existing checks and CI

For larger changes, explain the reasoning behind the implementation and any important tradeoffs.

## Development

Each repository may have its own setup, build, test, and contribution requirements.

Check the repository's `README.md`, local documentation, and package scripts before making changes.

Where repository-specific contribution instructions exist, those instructions take precedence over this organization-wide guide.

## Commit Messages

Keep commit messages concise and descriptive.

Examples:

```text
fix: handle invalid query payloads
feat: add collection index support
docs: update protocol documentation
test: add storage integration coverage
refactor: simplify request parsing
```

A strict commit convention is not currently required unless otherwise specified by the individual repository.

## Code Quality

Contributions should aim to be:

- Readable
- Maintainable
- Tested where appropriate
- Consistent with the surrounding codebase
- Focused on solving the underlying problem rather than adding unnecessary complexity

## Security

Do not report security vulnerabilities through public issues.

Follow the security reporting instructions provided by the affected repository.

If private vulnerability reporting is available, use it.

## Conduct

By participating in SinterDB projects and community spaces, you are expected to follow the organization's `CODE_OF_CONDUCT.md`.

## Questions

If you are unsure where to start, open a discussion or issue in the relevant repository and describe what you would like to work on.

Thanks for helping improve SinterDB.
